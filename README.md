### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах
- Пользователь не может самостоятельно интегрировать датчик в систему, требуется выезд специалиста
- Система поддерживает синхронное взаимодействие по REST-API
- Включение/отключение отопления происходит по запросу от сервера к датчику-термостату

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс
- Система получает данные о температуре с датчиков, установленных в домах
- Система поддерживает синхронное взаимодействие по REST-API

### 2. Анализ архитектуры монолитного приложения

- Язык программирования: Go
- База данных: PostgreSQL
- Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
- Взаимодействие: Синхронное, запросы обрабатываются последовательно.
- Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
- Развертывание: Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

- Домен "Управление пользователями" (User Management)
  - Регистрация

### **4. Проблемы монолитного решения**

* Синхронное взаимодействие, запросы обрабатываются последовательно, низкая скорость обработки запросов, риски потери команды при моментном обрыве связи сервера с датчиком
* Низкая изоляция, изменения в одной части приложения могут влиять на другие механизмы
* Трудная масшибируемость монолита, в часы пиковой нагрузки на отдельный механизм придется скейлить весь проект, что дольше и ресурсозатратнее
* Длительный цикл разработки и развёртывания, долгое тестирование и деплой всего проекта даже после незначительной доработке
* Труднее распределить работы в команде, труднее онбординг новых участников, т.к. знать нужно всё, сразу и много

# Задание 4. Создание и документирование API

### 1. Тип API

Взаимодействие пользователя и бэка будет синхронное по REST API. Пользователь запрашивает телеметрию, отправляет команды, редактирует профиль, управляет учетной записью.
Важно мгновенно видеть результат действий, иметь предсказуемый, простой и быстрый отклик для фронтенда.
Важно контролировать ошибки и текущие статусы, синхронно возвращать HTTP-коды (200, 400, 401, 500 и тд).
Важно иметь аутентификацию и авторизацию через JWT токен в REST.

Взаимодействие бэка с устройствами/датчиками будет асинхронное через Kafka и IoT MQ Broker - HiveMQ, тк. события могут быть высокочастотными и ненадёжными, устройства могут быть временно оффлайн.
Важно сохранять сообщения (команды, телеметрия) в топиках Kafka до потребления.
Важно не держать соединение с устройством постоянно, можно обрабатывать сообщения повторно в случае сбоя. 
Устройства могут находится в экономичном режиме, регулярно выходя из спячки, получая команду на выполнение и отправляя статус.
Kafka легко обрабатывает тысячи устройств и потоков телеметрии одновременно.
Потребителей можно горизонтально масштабировать, чтобы обрабатывать поток данных без блокировок.
Важно, чтобы бэк и устройства не зависили друг от друга во времени, отправка команды и получение телеметрии не блокировали UI.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081
3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

Ревьюер будет проверять точно так же.
